## 前提与假设

计划按“一人兼职、AI 编码助手辅助”估算；人力或投入时间变化时，工期按比例调整。

- **人力**：1 名开发者兼职，每周约 15–20 小时；编码主要借助 Claude Code 等 AI 编码助手，人负责设计、评审和验收
- **范围**：以架构文档中已定的 V1 范围为准：4 类核心链路（伺服电机、减速器、驱动器、轴承），每类 30–50 个型号，只做静态匹配
- **环境**：FreeCAD 1.x、Python 3.11+、PostgreSQL + pgvector、FastMCP、Claude API
- **日历**：12 月中旬到元旦预留 3 周缓冲，对应学期假期
- **原则**：任何范围或方案变更，先改架构文档和本计划，再动代码

## 开发方案：仓库结构与模块分工

采用单仓库（monorepo），按架构五层划分模块；`schema/` 是所有模块的共同契约，最先定稿、最少改动。

```text
freecad-ai-parts/
├── schema/            # 组件/端口/规则/系统的 JSON Schema，端口类型库 port-types/
├── kb/                # 数据库迁移、数据加载、查询 API、向量索引
├── ingest/            # 来源登记、采集、规格书解析、归一化、人工复核队列
├── engine/            # 链路模板、候选求解、性能链计算、校验器、排序与解释
├── mcp_server/        # FastMCP 工具（10 个）+ REST 接口
├── freecad_addon/     # FreeCAD 工作台：包络模板、端口坐标系、装配、干涉、对话面板
├── data/
│   ├── seed/          # 手工录入的样例型号
│   └── sources.yaml   # 来源登记：网址、许可、可用范围
├── tests/
│   └── golden/        # 标准测试集：已知正确 / 已知错误的组合
└── docs/              # 架构、schema 说明、决策记录
```

| 模块 | 依赖 | 首次用到的里程碑 | 可独立测试 |
| --- | --- | --- | --- |
| `schema` | 无 | M1 | 是：schema 校验样例数据 |
| `kb` | schema | M1 | 是：加载与查询单测 |
| `ingest` | schema、kb | M2 | 是：对样例 PDF 比对抽取结果 |
| `engine` | schema、kb | M3 | 是：golden 测试集 |
| `mcp_server` | engine、kb | M4a | 是：MCP 客户端调用测试 |
| `freecad_addon` | mcp_server | M4b | 部分：需 FreeCAD 环境 |

## 开发方法与质量保障

核心方法是 schema 先行、测试先行：先定契约和验收用例，再让 AI 编码助手按契约实现，人只在契约和验收上把关。

1. **schema 先行**：每个模块开工前，先写清输入/输出的 schema 和接口说明，放进 `docs/`，评审通过再编码。
2. **golden 测试集**：M1 起维护一组标准组合，包括已知正确的（应通过）和故意错配的（应拒绝，并给出正确原因）。配置引擎和 MCP 工具每次改动都要全部跑通。
3. **数据质量门槛**：规格书抽取的关键字段（额定扭矩、转速、轴径、法兰孔位等）每品类抽样人工核对，准确率达到 95% 再批量入库；低置信度字段自动进入复核队列。
4. **数据可追溯**：每个参数记录来源文件、页码、抽取时间和置信度，修改留历史；这和质量体系里的记录追溯是同一套思路。
5. **AI 编码的约束**：按模块下任务，每次改动附测试；不让 AI 同时改 schema 和实现；合并前人工评审 diff。
6. **持续集成**：每次提交自动运行 schema 校验、单元测试和 golden 测试集；FreeCAD 相关测试在本地运行（2026-10-01 起改为在 CI 的 `freecad` 作业中运行，ADR-0032）。
7. **决策记录**：重要取舍写成简短决策记录（ADR）存入 `docs/`，避免后面反复讨论同一问题。

## 风险与应对

最大的风险在数据层：规格书格式五花八门，端口信息常常不完整，这会同时拖慢 M2 和削弱 M3 的校验能力。

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 规格书缺少端口细节（如法兰孔位只在图纸里） | 接口校验无法进行 | 缺失字段标记为“未知”而非猜测；优先选图纸清晰的厂商；必要时从原厂 CAD 手工量取少量关键尺寸 |
| LLM 抽取准确率不达 95% | M2 延期 | 按品类细化抽取 schema 和提示词；表格类页面走专门的表格提取；提高人工复核比例 |
| 厂商使用条款不允许提取 | 数据源减少 | M2 第一周先完成许可核查；备选厂商名单；商业路线下直接申请数据授权 |
| 端口类型定义在 M3 才暴露缺陷 | 返工 schema | M1 就用 golden 用例压测 schema；schema 变更走决策记录 |
| FreeCAD 1.x API 与 Assembly 工作台变动 | M4b 延期 | 封装一层适配接口；锁定开发用的 FreeCAD 版本 |
| 兼职投入不稳定（课程、工作） | 整体延期 | 缓冲期吸收；每阶段结束重新估算剩余工期 |

**2026-09-30 新增风险与调整（ADR-0015）**：初查发现 Harmonic Drive、安川的网站条款禁止未经书面许可复制内容、自动采集和商业使用。应对：M1–M3 的开发和 golden 用例一律使用虚构测试组件；同时向候选厂商请求书面授权；种子数据（issue #7）移至 M2，取得授权后录入；若 10/26 仍无授权数据，M2 先用由虚构组件生成的合成规格书开发抽取流程。剩余风险：授权迟迟未到时，M2 的真实数据验收可能延后，M5 演示可能只用虚构或少量已授权组件。

## 工作节奏与计划维护

以周为单位推进，以阶段验收为关口；计划本身是活文档，先改计划再改代码。

- **每周开始**：从当前阶段任务中选定本周目标，写入任务清单
- **每周结束**：跑一遍 golden 测试集，记录完成情况和遇到的问题
- **阶段结束**：按验收标准演示；更新本计划的剩余工期；必要的方案调整先写进架构文档
- **变更规则**：范围、接口或 schema 的任何变更，先改文档、再动代码，保持实现与方案一致

## M6：公开数据跑通（2026-10-01 起）

V1 开发提前完成后，项目负责人决定开发不停，先用公开数据跑通真实数据流程，厂商授权不急（ADR-0040）。

- **取什么**：厂商公开发布的产品目录与规格书中的参数和接口尺寸；许可明确的开源硬件设计
- **不取什么**：文档、图片、图纸与 CAD 本身；需要登录或付费的资料；价格；也不批量爬取
- **怎么做**：规格书逐份登记、在 GitHub Actions 或 Codespaces 中下载并用真实 LLM 抽取，只把录制与抽取结果提交回仓库；关键字段由 AI 独立复核，不一致项留待人工核对
- **目标**：至少一套由真实组件（Harmonic Drive 减速器、安川 Σ-7 电机与驱动器等）组成的关节方案，从一句需求跑到 BOM、布局与 URDF

分项任务与验收见 [实施细则](implementation-rules.md) 的“M6 分项任务”。厂商授权仍可并行争取，取得后相应来源改为 `license: partner`。
