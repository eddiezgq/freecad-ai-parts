## 一、目标

17A 让工厂“看得见、点得通”。17B 让它**自己发现问题，并说清楚为什么、影响到谁**：

1. **异常检测**：按领域的规则库持续检查全厂，发现问题就生成一个“异常”对象。
   - 异常有严重度、负责角色、证据；
   - 有生命周期：新发现 → 已确认 → 处理中 → 已解决（条件消失时自动解除）。
2. **追因与影响面**：每个异常沿本体图双向走。
   - 往上游找“为什么”，往下游算“影响了谁、影响多大”；
   - 每一步都写明依据：哪条规则、哪些对象、哪条原始记录。
3. **指挥台 v1**：厂情中枢的新首页。
   - 第一屏“全厂态势”：15 个领域各一块态势卡；
   - 第二屏“异常处理”：三栏，即异常清单、因果链图、处理。推演（右栏的“如果这样做会怎样”）在 17C 加上。

这一期结束时，验收用的两个故事要能在网页上完整走通：
- **停机追到客户**：老师让精车 CNC-L01-B 停机 → 1 分钟内出现异常 → 因果链显示受影响的工序、工单、销售订单和客户，以及预计延期多少。
- **现场报警追到召回范围**：一台现场减速器轴承报警 → 追到它的输出轴 → GRD-01 上同一片砂轮 → 同一片砂轮磨出的其他轴 → 它们装在哪些设备上、属于哪些客户，形成“建议排查范围”。

## 二、决定（待确认）

| 编号 | 决定 | 理由 |
|---|---|---|
| B1 | **规则 = 目录（yaml）+ 检测函数（Python）**。<br>· 目录 `digital/ontology/rules/<领域>.yaml` 写每条规则的编号、名称、领域、严重度、负责角色、阈值参数、开关、说明和处理提示；<br>· 检测逻辑是 `hub/ont/rules/<领域>.py` 里的一个小函数，只读本体和已有计算模块（看板、SPC、MRP、成本、孪生），返回“发现”（对象、数值、证据）；<br>· 每条规则至少一个“该报”和一个“不该报”的测试 | 和 17A 的做法一致：yaml 管“有什么、阈值多少”，代码管“怎么算”。阈值老师可以改，不用改代码 |
| B2 | **异常存自己的表（`anomaly`），同时映射成本体里的“异常”对象**。<br>· 自己的表保存生命周期、指派、备注，不会因为本体重建而丢失；<br>· 本体对象用来搜索、出现在 360 页、和其他对象连线。<br>“异常”类型的成熟度从“后续各期生成”改为“已有”。为此本体增加一种通用链接“涉及”（目标可以是任何类型） | 本体是从总线历史推出来的，可以随时重建；异常的处理记录是人的操作，不能随重建清掉 |
| B3 | **去重和自动解除**：<br>· 同一规则、同一对象只开一个异常；再次触发只更新“最近一次”和次数，严重度升高时记一条事件；<br>· 条件连续 2 轮检测都消失才自动解除（防止来回跳），解除写明原因；<br>· 人工关闭的异常，同一条件 24 小时内再出现就重新打开并记一笔 | 不刷屏，也不漏 |
| B4 | **检测循环**：枢纽里的后台线程，每 30 秒在本体同步之后跑一轮全部启用的规则。<br>· 一轮在教学工厂规模下不超过 2 秒；<br>· 单条规则出错只跳过这条，并记在规则目录页上 | 老师注入事件后，1 分钟内看到异常 |
| B5 | **第一批规则 20 条，只做现在有数据的领域**（见第三节）。安全环保、人员、能源三个领域的规则先写进目录、标“待数据”，在领域包接入数据时启用。全貌地图和态势卡上照实显示“这个领域还没有规则在跑” | 不做空转的规则；缺口如实显示 |
| B6 | **现有“AI 提醒”并入规则库**：<br>· `hub/ai.py` 里 `evaluate()` 的 5 类检查（停机、刀具寿命、质量趋势、不合格品、订单延期和缺料）改写成规则，结果完全一致（测试核对）；<br>· 异常开出、升级时照旧发 `ai.alert` 总线消息，首页的提醒、AI 助手、实验 7 任务都不用改；<br>· 数字孪生自己的报警（`twin_event`）由“服务”领域规则读入，不重复报警 | 一个来源，不两套 |
| B7 | **追因与影响面 = 链路规则在本体图上走**。<br>· “链路规则”写在 `digital/ontology/rules/chains.yaml`：从哪种异常出发、沿哪些链接、到哪种对象、每一步怎么量化（如停机分钟 → 工序推迟 → 工单预计完工 → 订单余量）；<br>· 量化只用已有的计算：看板的订单预测、MRP、成本模块、孪生寿命模型，不另写估算；<br>· 结果存在异常上（节点、边、每条边的依据、数值），对象有变化时重新算；<br>· 任何对象的 360 页加一个“影响面”按钮，对这个对象临时跑一遍（不开异常）。<br>· 走图最多 8 跳；同一个对象只走一次；超过 200 个节点时截断并注明 | 和方案 3.3 的“典型链”一一对应；每条边都有依据，可核查 |
| B8 | **种子链路 6 条（本期有数据的）**：<br>① 设备停机 → 排在它上面的工序任务 → 工单 → 销售订单 → 客户（量化：预计延期天数、订单余量）；<br>② 质量判异 / 超差 → 测量 → 零件 → 加工记录 → 设备、刀具（上游：刀具寿命）；→ 同一刀具加工的其他零件（下游：复检范围）；<br>③ 现场设备报警 → 出厂总成 → 输出轴 → 砂轮 → 同一砂轮磨出的轴 → 它们所在的现场设备 → 客户（下游：建议排查范围）；<br>④ 缺料 / 低于安全库存 → 物料 → 用到它的物料清单 → 工单 → 销售订单（量化：缺口数量、最早需要日期）；<br>⑤ 工单成本差异超标 → 工序 → 调整、换刀工时与废品（上游：差异分解，与“经营与成本”页的数字一致）；<br>⑥ 订单延期风险 → 工单 → 瓶颈工序 → 设备状态（上游：为什么会晚） | 本期两个验收故事分别用到 ① 和 ③ |
| B9 | **AI 只负责“讲成人话”**：<br>· 链条和数值由规则算出，模板句子写成说明（规则版，始终可用）；<br>· 配了模型时可以点“润色”，按地区用已备案模型（国内 DeepSeek，美国 Claude），沿用 `hub/llm.py`；<br>· 模型只拿到链条和数值，不许增删事实；输出里的每个数字必须能在链条里找到，否则退回规则版 | 合规；不让模型猜 |
| B10 | **指挥台第一屏“全厂态势”**：15 个领域各一块态势卡，放在全貌地图同样的价值链布局里，每块显示：<br>· 1–2 个关键指标（见第四节）及近 7 天趋势；<br>· 开着的异常数（按严重度着色）；<br>· 规则在跑的条数，或“待接入：缺什么数据”。<br>点卡片进入第二屏并筛出这个领域的异常。<br>趋势从本期开始每天记录一次（表 `ont_metric_daily`）；历史数据能算的回算 7 天 | 一眼看全厂；缺口照实显示 |
| B11 | **指挥台第二屏“异常处理”（三栏）**：<br>· 左：异常清单。按严重度、时间排序，可按领域、状态、负责角色筛选；<br>· 中：因果链图。从左到右按“原因 → 异常 → 影响”排列，按领域着色；点边看依据（规则、对象、原始记录），点节点打开对象卡片；<br>· 右：处理。规则给出的说明和处理提示，以及确认、指派（角色）、备注、关闭（填原因）；快捷入口跳到已有页面（开 8D、车间终端、订单与计划、孪生）。右栏下方先占位“推演与建议（17C）” | 先把“发现—理解—处置”闭合；推演和动作框架在 17C |
| B12 | **入口开放给所有角色**（17A 时只给厂长、计划员和老师）。<br>· 各角色默认筛出自己负责的异常，例如质检员看质量领域；<br>· 学生看不到老师注入的情景（“质量问题情景”），只看到它造成的现象。追因链如果要经过这类对象，学生看到的链在那一步断开，标“原因待查”。这正是实验 7 任务 5 要学生自己找的 | 有了指挥台再全员开放（17A 第十节第 4 问已约定） |
| B13 | **规则目录页**（`/ont/rules`）：<br>· 列出全部规则：领域、严重度、开关、阈值、最近触发、本期触发次数、出错；<br>· 厂长（教师）可以改阈值和开关，每次改动记录谁、何时、从多少改到多少；<br>· “用历史检验”：把一条规则在过去 7 天的数据上跑一遍，显示它会报多少次、报在哪里（只算，不开异常） | 规则可调、可审计；教学上能讲“阈值怎么定” |

## 六、接口

- `GET /api/ont/anomalies?status=&domain=&role=`
- `GET /api/ont/anomalies/{id}`：详情，含链条、证据、备注
- `POST /api/ont/anomalies/{id}/ack | assign | note | close`
- `GET /api/ont/impact/{type}/{key}`：任何对象的临时影响面
- `GET /api/ont/situation`：态势卡
- `GET /api/ont/rules`、`POST /api/ont/rules/{id}`（改阈值、开关；厂长教师）、`POST /api/ont/rules/{id}/backtest`
- `POST /api/ont/anomalies/{id}/narrate`：AI 润色说明

全部按角色和敏感级别过滤（沿用 17A 的 A14）。

### 2. 与细则的偏差（已按此施工）

1. **检测频率是 20 秒，不是 30 秒，也没有另起线程（B4）**：直接接在原 AI 提醒的后台循环里（它本来就每 20 秒跑一次），这样提醒和异常是同一个来源。
2. **链路规则写在代码里（`hub/ont/chain.py`），没有单独的 `chains.yaml`（B7）**：每条链路都要调用不同的已有计算（订单预测、BOM 展开、成本、孪生），写成 yaml 反而难读。链路的说明在代码文件开头，帮助第七章有表格。
3. **因果链图改成竖排**：原因在上、异常居中、影响在下（B11 原写左右排）。中栏比较窄，横排时节点会缩得看不清。
4. **Q5“8D 逾期”改成“8D 久拖未关”**：开单超过 7 天未关闭就报。8D 单没有分步的计划日期，无法按步骤判断逾期。
5. **V2“同批多台”只算可能与制造批次有关的报警（轴承、输出轴）**：本地走故事二时发现，换油过期、散热变差的设备也被算成“同批”，这是误报。阈值 `kinds` 可在目录里改。
6. **同一批设备可能同时开两个 V2**：按砂轮一个、按工单一个。两种分组说明的问题不同，都保留。
7. **现场报警的链条多了一项**：同一片砂轮磨出、还没装机的轴（在库或在制），建议装配前复检。
8. **“只看我负责的”**：对操作工、质检员等岗位默认勾选，对厂长和老师默认不勾。
9. **“用历史检验”**：读当前状态的规则（停机、库存、订单预测）回看过去是近似结果，页面上写明了。
10. **规则的阈值和开关**存在 `ont_state` 里，改动记录存在 `rule_change` 表里。
